# 디자인 캔버스 시안

목표는 지금 앱과 구분이 안 될 만큼 같은 모양에서 바뀐 부분만 비교하게 하는 것이다. 새 디자인 언어를 만들지 않는다.

## 1. 규칙 읽기

- `docs/design.md`: 확정된 결정, 다시 제안하지 않는 것, 미결 항목
- `apps/web/AGENTS.md`의 "스타일링 규칙"·"디자인 규칙"
- admin 화면이면 `apps/admin-web/AGENTS.md`도 읽는다(PC 전용이라 폰 시안은 만들지 않는다). 스냅샷 스크립트는 web만 다루므로, admin은 `pnpm dev`(Docker 필요)로 띄운 :3100을 PC 폭으로 열어 직접 보고(스크린샷) 해당 화면 코드에서 그린다.

## 2. 지금 화면 스냅샷 뜨기

시안의 "지금" 보드는 손으로 그리지 않고 실제 앱을 렌더링한 결과에서 시작한다. 코드만 읽고 그리면 HeroUI 기본값·상속 글꼴·배치·장식(불꽃 후광, 랠리, 유리 탭바)이 실제와 달라진다.

1. 처음 한 번 `pnpm install`과 `pnpm exec playwright install chromium`을 실행한다.
2. `pnpm design:snapshot`을 실행한다. Docker도 `pnpm dev`도 필요 없다. 스크립트가 web(Vite)만 빈 포트에 직접 띄우고(`DESIGN_SNAPSHOT_PORT`로 지정할 수 있다), 로그인·API·아바타 요청은 저장해 둔 응답(`scripts/design-snapshot/fixtures/responses.json`)으로 답하며, 브라우저 시계를 녹화 시각에 고정한다. 그래서 화면 모양은 지금 코드이고, 데이터는 녹화 때의 dev mock 데이터다. 인자 없이 실행하면 폴더를 비우고 전부 다시 찍고, 화면 이름을 주면(`pnpm design:snapshot home ranking`) 그 화면만 덮어쓴다. 결과는 `.design-snapshots/`에 쓴다(커밋하지 않는다).
   - 여러 사람·워커가 같은 저장소에서 동시에 찍을 때는 실행마다 출력 폴더를 나눈다(`DESIGN_SNAPSHOT_OUT=.design-snapshots/<작업 이름> pnpm design:snapshot`). 포트는 실행마다 따로 잡히지만 폴더가 같으면 전체 실행이 다른 실행의 결과를 지운다.
   - `<화면>.png`: 실제 모습. 시안과 비교하는 기준이다.
   - `<화면>.html`: 실제 DOM(앱의 Tailwind 클래스 그대로). 같은 폴더의 `app.css`(앱 CSS 전체)를 붙이면 앱과 똑같이 렌더링된다.
   - `index.html`: 찍은 화면을 한눈에 보는 페이지
   - 회원 아이디는 실제 회원 아이디로 녹화돼 있다(dev mock 회원을 실제 회원 아이디로 바꾸고 겹치는 줄은 하나만 남긴다). 로그인 회원은 brad.ley다.
3. "녹화 응답이 없는 요청"이 출력되면 API나 화면이 바뀐 것이다. 요청은 그대로인데 응답에 새 필드가 생긴 경우(새 기능이 화면에 안 보임)도 같다. Docker가 있는 환경에서 `pnpm dev`를 띄우고 `pnpm design:snapshot --record`로 다시 녹화해 `responses.json`을 함께 커밋한다. 녹화는 시각을 맞추기 위해 항상 전체 화면을 돌고, 로컬 주소의 응답만 저장한다(운영 Storage를 가리키는 아바타 등 로컬이 아닌 요청은 막고 목록만 남기며, 재생에서도 실패로 돌려줘 이니셜로 보인다). dev mock 아이디는 실제 회원 아이디로 바꿔 저장하고 로그인 토큰은 저장하지 않는다.
4. 필요한 화면이 목록에 없으면 `scripts/design-snapshot/snapshot.mjs`의 `SCREENS`에 단계를 추가하고 다시 녹화한다(지금: home, schedule, ranking, me, plus-menu, record-sheet, match-detail, profile, settings). dev mock에 없는 상태(빈 날, 세션 없는 날 등)는 해당 화면 HTML을 복사해 내용만 고친다.

스냅샷을 만들 수 없을 때만 예외로 해당 화면 컴포넌트와 `apps/web/src/components/ui/`, `apps/web/src/index.css`의 `@theme`를 읽어 그리고, 실제 화면과 대조하지 못했다는 사실을 사용자에게 알린다. 예전 디자인 캔버스(아티팩트)는 그 시점의 시안이라 지금 앱과 다를 수 있으므로 모양의 기준으로 쓰지 않는다.

## 3. 안 그리기

- 안 A·B는 "지금" HTML을 복사해 바뀌는 부분만 고친다. 고칠 때는 앱 코드와 같은 Tailwind 클래스(`bg-pk-primary`, `rounded-pk-lg`, `text-pk-15` 등)를 쓴다. `app.css`에 없는 클래스(앱 어디서도 안 쓰는 클래스)는 적용되지 않으므로, 새로 필요한 스타일은 `style=""`에 `index.css` `@theme`의 실제 값으로 쓴다.
- 새 화면이나 새 부품도 가까운 화면 HTML에서 비슷한 부분(카드, 경기 줄, 시트 틀)을 떼어 와 조립한다.
- 고친 보드는 브라우저(Playwright 등)로 렌더링해 "지금" PNG와 나란히 보고, 바꾸지 않은 부분이 그대로인지 확인한다.

## 4. 캔버스 구성

- 디자인 캔버스는 Artifact 도구의 Design 타입으로 만들고, 폰 화면 하나가 보드 하나다. 보드에서 `app.css`를 공용 파일로 불러올 수 있으면 그렇게 하고, 안 되면 보드마다 `<style>`로 넣는다. 계정에 연결된 디자인 시스템이 있어도 이 저장소의 화면이 우선이다. 디자인 시스템을 고르라는 단계가 나오면 쓰지 않는 쪽(`design_systems: false`)을 택한다.
- 첫 보드는 항상 "지금"(현재 화면 그대로)이고, 그 옆에 "안 A", "안 B" …를 같은 크기·같은 데이터로 나란히 둔다. 추천안이 있으면 이름에 "(추천)"을 붙인다.
- 폰 화면 보드는 390 × 844 기준이다. 스크롤이 긴 화면은 스냅샷 높이(파일 맨 위 주석)를 그대로 쓴다.
- 상태가 여러 개인 화면(참여 전/후, 진행 중/끝남, 빈 상태)은 상태별 보드를 따로 둔다.
- 보드마다 무엇이 바뀌었는지 한두 줄 메모를 붙인다.

## 5. 예시 데이터

- 아이디는 스냅샷에 나온 실제 회원 아이디를 그대로 쓴다. 새로 필요하면 같은 녹화본의 다른 회원 아이디를 쓰고, `dev_alice` 같은 개발용 이름이나 Player 1 같은 자리 채우기 이름, 지어낸 아이디를 쓰지 않는다.
- 평점은 2.5~4.5 사이 소수 셋째 자리(예: 3.214), 점수는 11점제(듀스는 15:14까지)로 쓴다. 평점 없음은 "–"다.

## 6. 마무리

- 사용자가 안을 확정하기 전에는 코드·이슈 작업을 시작하지 않는다.
- 확정되면 결론을 `docs/design.md`(또는 구현 규칙이면 `apps/web/AGENTS.md`)에 반영한다. 거절된 안은 `docs/design.md`의 "다시 제안하지 않는 것"에 더한다.
